SECTION 01

Executive overview

Huscribe Revenue OS (internally the Outbound Intelligence Engine, package name oie) is an end-to-end sales control plane: a private TypeScript ESM monorepo that discovers and enriches accounts, qualifies them by real conversation through a voice agent, scores them deterministically, and routes the best ones into a human-gated close. It is a single operator-facing product, live in production behind operator login.

This report answers two distinct questions that are easy to conflate. The first is how the running product is architected: its packages, its data model, its orchestration, its deployment. The second is the more interesting and more often misunderstood one: how the software was built, because it was assembled largely autonomously by an AI agent over an eight hour window.

The headline answer: did we use LangGraph?

No. The build used no third-party agent framework. Not LangGraph, not LangChain, not LlamaIndex, not CrewAI, not AutoGen, not OpenAI Assistants or Swarm. There is no Python agent graph anywhere. The orchestration was Claude Code native, built from two primitives: a cron-driven autonomous loop that re-invoked the top-level agent on a fixed cadence, and the Claude Code Workflow tool, a deterministic JavaScript orchestrator whose nodes are full tool-using Claude sub-agents. Control flow was plain deterministic code, never model-driven routing.

So there are two orchestration stories that sit on top of each other. The product runtime uses Inngest for durable workflow execution (retries, multi-day delays, resume-after-deploy). The product build used the two Claude Code native layers described in Section 2. These are independent: Inngest never built anything, and the agent loop is not part of the shipped product.

SECTION 02

Build-time multi-agent orchestration

This is the architecturally novel part. The system was built by composing two Claude Code native orchestration layers: a durable autonomous loop for cadence and resumability, and the Workflow tool for deterministic parallel sub-agent fan-outs inside individual firings.

Layer 1: the autonomous cron loop

The operator left the machine running, kept awake with the macOS caffeinate tool, and authorized full autonomy for roughly eight hours. A session-only cron job (created with Claude Code's CronCreate, id 7e46fd64, firing at minutes 8, 33, and 58, about every 25 minutes) re-invoked the top-level Claude agent with a fixed AUTONOMOUS BUILD LOOP prompt. Each firing was one bounded, verified increment.

Every firing followed a contract file, docs/autonomous/LOOP.md. The contract is the determinism: it removes the need for the model to improvise the meta-procedure.

  1. Check the clock. Read STARTED_AT.md; if now is at or past STOP_AFTER_EPOCH (or the backlog is fully checked), self-terminate.
  2. Orient. Read BACKLOG.md and the tail of PROGRESS.md.
  3. Work. Take the next 1 to 3 backlog items; do one verified increment; use a Workflow for substantial or parallel work.
  4. Verify before done. Typecheck, lint, test, or a Next.js build, plus live curl checks for deploys. Show evidence.
  5. Ship. Commit and push to the working branch; at a milestone open or merge a PR to main if checks pass.
  6. Record. Tick the backlog; append evidence to PROGRESS.md.
  7. Stop this firing. Do not spin; the next tick continues.

File-based blackboard state

Memory between firings is a durable Markdown blackboard on disk. Nothing relies on a single long-lived process or an in-memory context that a compaction would erase.

FileRoleProperty it provides
LOOP.mdThe firing contractDeterminism across firings
BACKLOG.mdThe plan plus a recurring cycle logShared goal state
PROGRESS.mdAppend-only evidence per firingAuditable history, resumability
STARTED_AT.mdThe 8 hour window and stop epochSelf-termination boundary

This blackboard is exactly what made the loop resumable across firings and context compactions, and able to self-terminate with CronDelete at the window end. Cron job 7e46fd64 did in fact delete itself at the boundary, with a final summary appended to PROGRESS.md. This is a scheduled-re-invocation pattern, a durable agent loop, and it is distinct from the Workflow tool below.

Layer 2: the Workflow tool

Inside firings that needed substantial or parallel work, the agent used Claude Code's Workflow primitive: a deterministic JavaScript orchestration script. Its hooks are agent(prompt, opts), parallel(thunks) (a barrier), pipeline(items, ...stages) (no barrier, stage-per-item), phase(title), and log(msg).

The crucial properties: agent() returns the sub-agent's text, or a JSON-schema-validated object when a schema is supplied (structured output is forced via a StructuredOutput tool the sub-agent must call, and the model retries until valid). Each node is a full Claude sub-agent with tool access (Read, Write, Bash, Grep, Glob, WebSearch, MCP). The control flow, the fan-out, the loops, the conditionals, the barriers, is plain deterministic JS. Concurrency is capped at about min(16, cpu cores minus 2); runs are journaled and resumable.

Where it was used (a)

A 24-agent docs run, organized in phases: 4 parallel research agents, then 10 doc-writer agents, then 7 module-guide agents writing per-folder AGENTS.md, then 3 strategy agents. The script wf-docs-md-strategy.js in docs/autonomous/ is the artifact.

Where it was used (b)

Producing both HTML reports as a gather to compose to verify to fix shape: gather facts, compose the artifact, run separate adversarial reviewer agents to fact-check and design-check it, then a fix agent applies the returned issues.

Patterns applied

Parallel fan-out with a barrier; pipeline (stage-per-item, no barrier); explicit phases; structured outputs via JSON schema; and adversarial, independent verification, where separate reviewer sub-agents fact-check and design-check the artifact and return issues for a fix agent to apply.

Verification discipline (woven through both layers)

Nothing was called done without evidence: typecheck, lint, test, or a Next.js build, plus live curl checks for deploys. Every PR was gated on CI, a verify job (turbo run typecheck lint test build) plus a gitleaks secret scan, before merge. Generated artifacts were adversarially reviewed by independent sub-agents. A secret scan ran before each commit.

Evidence anchor

15 PRs merged to main across 18 cycles, every one CI-gated. The CI files are real: .github/workflows/ci.yml (the verify job) and .github/workflows/secret-scan.yml (gitleaks-action v2, with pull-requests: read so it can list PR commits).

SECTION 03

Framework comparison

An honest positioning. The Claude Code Workflow tool is conceptually in the same family as LangGraph: deterministic, code-defined orchestration over LLM nodes with structured I/O and journaling or resume. It is a different runtime, and its nodes are tool-using Claude agents rather than graph-library nodes. None of the frameworks below were used in this build.

Explicit: what was and was not used

Used: Claude Code native primitives only. The cron-driven autonomous loop (Layer 1) and the Workflow tool (Layer 2), both Anthropic / Claude Code native.

Not used at any point: LangGraph, LangChain, LlamaIndex, AutoGen, CrewAI, OpenAI Assistants or Swarm, or any other third-party agent framework. There is no Python agent graph, and control flow was deterministic code, not model-driven routing.

The fair summary: if you already think in LangGraph terms, the Workflow tool will feel familiar (deterministic code orchestrating LLM nodes, structured I/O, resumability). The difference is that each node here is a sandboxed Claude agent with the full Claude Code tool surface, and the durable cadence came from an external cron re-invoking the top-level agent rather than from a long-running graph process. The frameworks above are all capable, mature tools; they were simply not the chosen path here.

SECTION 04

Product runtime architecture

A private TypeScript ESM monorepo using pnpm workspaces (pnpm 10.33.0, Node 20.11 or newer) with Turborepo as the task runner. Workspace globs are packages/* and apps/*: exactly 5 internal packages plus one Next.js 15 app.

The monorepo and its 5 packages

Internal packages are consumed as raw TypeScript source via the "." export pointing at ./src/index.ts; noEmit is set everywhere, and tsx plus Vitest transpile. Turbo orchestrates typecheck, lint, test, and build with dependsOn ^build and ^typecheck for topological ordering; pnpm verify runs all four. The shared tsconfig.base.json is strict ES2022 / ESNext / Bundler with verbatimModuleSyntax, isolatedModules, and noUncheckedIndexedAccess.

The flywheel pipeline

The product is a flywheel: every voice call makes the master database more valuable. That is the verify-by-conversation moat.

Deterministic scoring: the LLM never scores

The crown jewel is in @oie/core: a pure, deterministic, explainable ICP scoring engine. scoreLead(subject, icp, now) turns a vendor-agnostic ScoringSubject plus a Zod-validated IcpProfile into a ScoreResult of fit, intent, composite, and tier, with a full rationale. Code computes every number. The LLM never computes, adjusts, or emits fit, intent, composite, or a tier; models only extract and reason over source text.

  • Fit is a weight-normalised average over up to eight firmographic, technographic, people, and keyword dimensions, each scored 0 to 100 with a known flag, so missing data scores zero and lowers coverage rather than being guessed.
  • Intent groups signals per ICP criterion, applies linear time-decay from detection to expiry, combines multiples of one type with probabilistic-OR diminishing returns (1 minus the product of (1 minus s)), then weight-normalises.
  • Composite is blend.fit * fit + blend.intent * intent (blend validated to sum to 1); assignTier maps composite to A, B, C, or D using ICP thresholds (D is the implicit below-C bucket).
  • Purity is strict: the only non-pure input is the caller-passed now. Same input plus same now yields byte-identical output. SCORING_MODEL_VERSION (currently scoring-v1) is stamped on every score and must be bumped on any computation change.

The enrichment waterfall

enrichCompanyWaterfall calls EnrichmentProviders in priority order, merges only still-missing fields with per-field source attribution, stops early once a record is complete-enough (we own the cost ceiling), and falls through provider errors rather than aborting. collectSignals is the signal analogue, with cross-provider dedup via signalDedupeKey (keeping the stronger signal so intent is never double-counted) and central decay windows. The cascade, fallback order, and cost ceiling live in our orchestration core, never in any adapter.

The send-gate and DRY_RUN

The single most dangerous action, a real send, is guarded by evaluateSendGate in send-gate.ts (ADR-0009): a pure, total function. Two independent conditions must both hold for a real send: DRY_RUN off (system-level) AND explicit per-action human approval. LinkedIn and WhatsApp carry a third gate (GATED_CHANNELS), the channel must be operator-enabled, off by default.

DRY_RUN always wins

DRY_RUN defaults true everywhere and always wins: it returns outcome simulate regardless of approval. Flipping DRY_RUN alone can never send, and an approval can never override DRY_RUN. executeSendStep is the only place that calls an adapter's .send(), and only when allowSend is true. Defence in depth adds a deny rule, a PreToolUse hook, and adapter-level dryRun honoring.

Inngest durable orchestration

The runtime brain is the in-repo packages/orchestration logic wrapped by Inngest durable step functions (ADR-0002). Inngest provides retries, exactly-once-by-memoisation, durable multi-day delays, resume-after-deploy, and event-driven cancellation. runEnrolment wraps every operation in step.run (memoised on replay) and uses step.sleepUntil for multi-day cadences. The gate and approval check run on every execution including replays, never memoised away. The production pipeline reaches vendors over REST and webhooks only, never MCP; the send-path is never behind an interactive MCP call.

Anti-corruption adapters

Every bought rail (Clay, Apollo, Explorium, Places, SearchApi, TheirStack, PredictLeads, Exa, Smartlead, Resend, Unipile, HubSpot, the LLM, NOVA) is wrapped in an adapter implementing one of five stable internal interfaces: EnrichmentProvider, SignalProvider, EmailSender, MessagingChannel, CrmStore. Each validates the raw wire payload with Zod inside its own mapper.ts, folds vendor free-text enums onto closed OIE enums (emitting unknown rather than guessing), records per-field provenance in a sources map, and converts vendor errors to a typed AdapterError taxonomy. A shared base layer provides an injectable HTTP transport seam (fixtures in CI), retry with full-jitter backoff, and deterministic sha256 idempotency keys. Only adapter classes are exported; mappers stay internal.

Anthropic SDK usage and model tiering

AI features (Close Room, Knowledge, Voice Dojo) call Claude through one client, apps/web/lib/llm.ts, which wraps the engine's LlmClient from @oie/integrations. There is one Anthropic client, one set of model ids, one place that reads the key. The key is server-only, read lazily from process.env, never NEXT_PUBLIC_ and never logged. The LLM reasons over text; code computes every number.

SECTION 05

Voice and NOVA

The Revenue OS dogfoods Huscribe's own voice agent, NOVA, a separate service (FastAPI plus LiveKit at api.novalabs.ae). The calls that build the database are the product.

The 4-phase agent

NOVA runs a fixed conversational arc: Greeting, Discovery, Pitch, Close, handed to NOVA's DSPy pre-call context. Integration is via scripts/nova-call.ts: it pulls awaiting_approval leads from the master DB, places a call (POST /calls), polls (GET /calls/{id}), and ingests CallSession plus CallFinding rows. The POST body carries owner_email, product, leads, context, goal='qualify_interest', language, consent=true, and an idempotency key. Phones are normalised to E.164 (UAE-aware) by toE164().

Compliance gate, demo versus live

DEMO_MODE: no live PSTN

demoMode is computed as !NOVA_API_KEY. Both place_calls and get_call are public (no token); the optional NOVA_API_KEY Bearer is what flips demoMode off. By default, calls only join a LiveKit room named call-<context_id> with no PSTN dial. demoMode is persisted on every CallSession. NOVA's own compliance gate (consent, DNCR, calling-window) plus owner sign-off are prerequisites before any real PSTN dial, aligned to UAE Cabinet Resolution 56 of 2024 and PDPL (Federal Decree-Law 45 of 2021).

CallSession and CallFinding

On accept, each call is upserted as a CallSession (status pending, unique novaCallId, consentBasis='operator_initiated_demo'). ingestCallResult updates transcript, summary, outcome, cost, and opt-out, replaces CallFinding rows, and enriches the master DB only if the session is consented: mobile maps to Contact.phone / whatsapp; tools maps to Company.techStack plus a tech_adoption Signal.

Findings pass through a pure anti-corruption function, nova/findings.ts, which keeps only seven canonical, consented keys: identity_confirmed, after_hours_handling, tools, monthly_volume, mobile, demo_interest, opt_in. It drops any non-canonical key, ignores null or empty values (never fabricates), coerces booleans to yes or no, clamps to 500 chars, and only keeps a confidence in 0 to 1.

The moat

Every consented call writes verified, first-party facts straight into the master DB. Competitors buy the same vendor data; only this system holds the verify-by-conversation layer on top of it. That compounding, owned dataset is the durable advantage.

SECTION 07

Deployment and security

A single-stage Docker image (node:22-slim) on Fly.io, app huscribe-revenue-os, primary region fra, currently live at release v12.

Fly deploy posture

  • Image: single-stage node:22-slim, built on a Fly remote builder. The build runs with inline throwaway placeholder env (DATABASE_URL, AUTH_SECRET) so no real secret persists to a layer. @oie/db postinstall runs prisma generate.
  • Scale-to-zero: auto_stop_machines='stop', auto_start_machines=true, min_machines_running=0; shared-cpu-1x / 1024 mb; force_https; concurrency soft 180 / hard 220.
  • IPv4: a dedicated IPv4 (109.105.222.142) was allocated so the app routes from IPv4-only networks, after the hostname initially had only an AAAA record.
  • Health check: Fly runs GET /api/health every 30s; on deploy it waits for the check to pass before marking a release healthy. The endpoint is a pure no-auth, no-DB liveness probe returning 200 JSON, so a DB or provider blip cannot flap health and trigger restarts.

Auth and headers

Auth is Auth.js v5 (next-auth 5.0.0-beta.31) with JWT sessions (12h maxAge, 1h updateAge), trustHost:true baked in, and an authorized callback allowlisting /signin, /api/health, /api/auth, /api/inngest. Login is operator email plus a bcrypt hash (bcryptjs); no DB adapter; fail-closed if creds are absent in production. next.config.mjs applies a full security header set on every route: a CSP, HSTS with preload (max-age=63072000; includeSubDomains; preload), X-Frame-Options DENY, nosniff, Referrer-Policy, and a Permissions-Policy disabling camera, microphone, geolocation, and browsing-topics. poweredByHeader is false.

Secrets and CI gates

Every secret (DATABASE_URL, AUTH_SECRET, ANTHROPIC_API_KEY, AUTH_OPERATOR_*, provider keys, NOVA_API_KEY) is set via flyctl secrets set and injected at runtime only; fly.toml and the image carry only non-secret env. CI gates: a verify job plus a gitleaks secret scan, both required before merge.

Flagged doc discrepancy (not invented)

SECURITY.md is stale on two points: it lists the security headers and trustHost:true as not-yet-shipped backlog items, but both are already implemented in next.config.mjs and auth.config.ts respectively. The code is the source of truth here.
