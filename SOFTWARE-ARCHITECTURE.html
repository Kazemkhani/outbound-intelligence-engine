Huscribe Revenue OS Software Architecture

The architecture of Huscribe Revenue OS

A private pnpm + Turbo TypeScript monorepo (codename OIE) that discovers, enriches, scores, and human-gates B2B outreach. The LLM writes copy and reasons; deterministic code owns every number; nothing sends without a passing dry-run and explicit human approval.

01 System overview and package graph

Huscribe Revenue OS (the repository is named oie) is a layered outbound-intelligence engine. Five internal libraries form a clean dependency DAG with the pure domain core at the root, and a single Next.js 15 application (apps/web, package name web) is the control plane on top.

The system is organised around four architectural ideas that recur in every layer:

  • A pure deterministic core. @oie/core depends only on zod. It owns the domain vocabulary, the Zod-validated ICP config, the normalised fact view of a lead, and the entire scoring engine. No LLM, no I/O, no wall-clock.
  • An anti-corruption boundary. @oie/integrations wraps every bought rail (enrichment, signals, email, messaging, CRM, voice, LLM) behind five stable internal interfaces, translating vendor JSON into unified DTOs. Vendor shapes never escape a mapper.
  • An orchestration brain. @oie/orchestration holds pure decision functions (send-gate, sequence state machine, waterfall, cost caps) wrapped by Inngest durable steps. The scoring-bridge lives here so that pure core never imports the integration layer.
  • A human-gated control plane. apps/web renders the operator UI, runs all AI surfaces through one ask() chokepoint, and routes every send through the code-level send-gate. DRY_RUN is surfaced everywhere.

Figure 1.1 - System context and package-dependency graph (a DAG, core at the root)

Solid gold = the consume edge from the UI. Grey = workspace dependency edges. Dashed teal = network boundary, crossed only by adapters. @oie/integrations is NOT in next.config.mjs transpilePackages; it is pulled transitively.

Layering invariant The edges only ever point down. @oie/core imports nothing from @oie/integrations or @oie/db. The DTO-to-fact conversion (scoring-bridge) is deliberately hoisted into @oie/orchestration so the pure core stays free of the integration layer.

03 Domain core and the deterministic scoring engine

@oie/core owns the entire scorer as a pure function. scoreLead(subject, icp, now) never reads the clock and never imports an LLM SDK. The only "LLM" token in the whole package is a doc comment in icp.ts saying the LLM never computes the number.

Key signatures

// packages/core/src/scoring-engine.ts

    intent: { score; criteria: IntentCriterionResult[] };

  };
};

// packages/core/src/scoring.ts  -  math primitives (unit-tested in isolation)
clampScore(n)            // -> [0,100]
weightedScore(items)    // clamp( sum(clamp(score_i)*w_i) / sum(w_i) )
compositeScore(fit, intent, blend) // clamp( clamp(fit)*blend.fit + clamp(intent)*blend.intent )
signalDecayFactor(detectedAt, expiresAt|null, now)
assignTier(composite, thresholds)    // A|B|C|D, >= inclusive

The fit / intent / composite / tier math

Fit: weighted average over configured dimensions only

Up to 8 candidate FitComponents are built (industry, employeeCount, revenue, geography, localCategory [nullable], technographics, people, keywords), then filtered to c !== null && c.weight > 0. Weight-0 dimensions are dropped entirely.

fit = weightedScore(components)
= clamp( Σ clamp(score_i)·w_i / Σ w_i )

coverage = knownCount / components.length is reported in the rationale but does not scale the fit number: a known-but-zero and an unknown component both contribute score 0.

Intent: strength × time-decay, diminishing returns

Per criterion (weight > 0), surviving signals each yield

s_i = (clamp(strength·100)/100) · decay(detectedAt, expiresAt, now)

folded by a probabilistic-OR:

combined = 1 − &Prod;(1 − clamp(s_i))

score = clamp(combined·100). One strong fresh signal dominates; many weak ones saturate slowly. Overall intent is the weightedScore across criteria.

// Per-dimension fit sub-scores (each 0..100)
industry / revenue / localCategory : 100 if matchesAny (fuzzy substring) else 0
employeeCount  : 100 inside [min,max]; else clamp(100 - 100*dist/width)
geography      : country match -> 100; else region -> 100; else haversineKm <= radius.km -> 100; else 0
technographics : any AVOIDED tool present -> 0 (hard disqualify); else clamp(100*min(matched,2)/2)
people         : clamp(titleHit*50 + seniorityHit*25 + deptHit*25)   // title is the dominant 50pt signal
keywords       : any EXCLUDE term -> 0; else clamp(100*hits/min(include.length,2))

// Time decay (scoring.ts): linear from detection to expiry
signalDecayFactor(detectedAt, expiresAt, now):
  expiresAt == null            -> 1      // no decay
  span = expiresAt - detectedAt; span <= 0 -> 0
  remaining = clamp01( 1 - (now - detectedAt) / span )    // 1 at detection, ~0.5 at midpoint, 0 at/after expiry

// Composite + tier (seed/test ICP: blend {fit:0.6, intent:0.4}; thresholds {A:80, B:65, C:50})
composite = clamp( clamp(fit)*0.6 + clamp(intent)*0.4 )    // blend is Zod-refined to sum to 1
tier      = composite >= 80 ? A : >= 65 ? B : >= 50 ? C : D

Signal TTL windows feed the decay and live in one place, signal-windows.ts: DEFAULT_SIGNAL_TTL_DAYS = { funding 90, tech_adoption 60, job_change 45, hiring 30, news 30, web_change 21 }. Adapters never set their own expiry; signalExpiry(type, detectedAt, ttlDays?) centralises it so ingestion and scoring stay in agreement.

The LLM is kept out structurally, not by convention packages/core/package.json declares exactly one runtime dependency: zod ^3.24.1 (no @anthropic-ai/*). scoreLead's signature is (ScoringSubject, IcpProfile, Date) => ScoreResult: there is no model client, prompt, or string-from-LLM input path, so there is no surface for a model to inject a number. A determinism test asserts scoreLead(perfect, icp, NOW) deep-equals a second call.

The fact view (anti-corruption inside core). The engine consumes only CompanyFacts, ContactFacts, and SignalFact (each field optional; missing scores zero and is recorded as unknown, never guessed), wrapped as ScoringSubject {company, contact, signals[]}. No vendor field reaches the engine. Identity helpers in dedupe.ts (companyDedupeKey, contactDedupeKey, signalDedupeKey) are pure so vendor shapes never decide identity.

Shared base and central decay ownership

base/errors.ts: AdapterError with kind (auth | rate_limit | not_found | invalid_request | provider_unavailable | timeout | unknown); kindFromStatus maps 401/403→auth, 404→not_found, 429→rate_limit, 4xx→invalid_request, 5xx→provider_unavailable. base/retry.ts: withRetry applies per-attempt withTimeout and full-jitter exponential backoff (backoffDelay = floor(rand()*min(max, base*2^attempt))). base/http.ts: HttpTransport seam with fetchTransport (prod) and stubTransport (replays a fixed queue) so CI runs with no live calls. 06 Runtime orchestration and the send-gate

@oie/orchestration is the brain: pure, deterministic decision functions wrapped by Inngest durable step functions that own retries, multi-day sleeps, exactly-once replay, and all DB/AuditLog persistence. The load-bearing safety rail is evaluateSendGate in send-gate.ts: a pure, total function gating every provider send.

The data flywheel

Figure 6.1 - The data flywheel: discover -> enrich waterfall -> NOVA voice -> master DB -> deterministic score -> human-gated close

The send-gate decision logic

// packages/orchestration/src/send-gate.ts  -  pure and total, fixed precedence
function evaluateSendGate(input: {
  dryRun: boolean; approval: "pending"|"approved"|"rejected";
  channel: Channel; channelEnabled: boolean;
}): SendGateDecision {
  // (1) channel opt-in first
  if (GATED_CHANNELS.includes(channel) && !channelEnabled) -> "blocked_channel_disabled", allowSend false
  // (2) rejection beats DRY_RUN
  if (approval === "rejected")                     -> "blocked_rejected",        allowSend false
  // (3) DRY_RUN ALWAYS WINS, even over an approved action
  if (dryRun)                                    -> "simulate",               allowSend false
  // (4) must be human-approved
  if (approval !== "approved")                  -> "blocked_awaiting_approval", allowSend false
  // (5) the ONLY allowSend=true branch
  else                                           -> "send",    allowSend true
}

Figure 6.2 - Send-gate decision flow (allowSend=true is the only path that permits a provider call)

Three independent conditions must all hold for a real send: (1) channel operator-enabled (LinkedIn/WhatsApp off by default), (2) DRY_RUN off, (3) human-approved. DRY_RUN defaults true everywhere (boolFromEnv(true)); a missing or blank value resolves to true and must be explicitly set to a falsy token to live-send.

executeSendStep: the only place that calls an adapter .send()

send-step.ts layers gates in order: (1) isSuppressionMatch (email==email OR domain==domain, case-insensitive, email only) returns 'suppressed' with status 'failed' and no provider call; (2) evaluateSendGate: if !allowSend, maps via gateOutcomeToStepOutcome (simulate→dry_run, blocked_awaiting_approval→awaiting_approval, blocked_rejected→rejected, blocked_channel_disabled→channel_disabled) and pendingMessageStatus (simulate and blocked_awaiting_approval both → 'awaiting_approval' so dry-run previews sit in the approval queue); (3) only on allowSend === true it builds AdapterContext { dryRun: false, idempotencyKey, signal } and calls emailSender.send or messagingChannel.send. The idempotency key is stable across replays: enrolment:${enrolmentId}:step:${stepIndex}:channel:${channel}.

The enrichment waterfall

enrichCompanyWaterfall(query, providers, ctx, options) iterates providers in priority order: unconfigured providers push a skipped_unconfigured trace; each result.cost is pushed and ctx.recordCost?.(cost) called; on a match, mergeCompany fills only fields still missing across COMPANY_FIELDS and records the supplying provider per field in company.sources; isComplete (default domain && industry && employeeCount) triggers an early break to stop spend. A thrown AdapterError is caught, recorded as an error trace, and the cascade falls through to the next provider rather than aborting. collect-signals.ts is the analogue: it fans in across SignalProviders, dedupes via signalDedupeKey keeping the stronger strength on collision, and assigns central decay via signalExpiry when an adapter set none.

Inngest durable cadence (runEnrolment)

inngest = new Inngest({ id: 'oie' }). runEnrolment id 'sequence-enrol', retries: 3, cancelOn oie/sequence.stop. Per step, memoised step.run: (1) check-stop-pre-sleep (cost caps + stop events), (2) step.sleepUntil(nextDueAt(...)) for durable multi-day delay, (3) check-stop-post-sleep (a reply may have arrived), (4) load-suppressions then executeSendStep + prisma.message.create (externalId = idempotencyKey) + AuditLog, (5) advance-state via pure advance(state, steps, now). Date fields are re-hydrated from ISO strings because step.run serialises through JSON.

DRY_RUN, approval queue, cost caps

  • The approval queue today is a DRY_RUN stub: approveMessage/rejectMessage in apps/web/app/approvals/actions.ts record intent via console.info only and contact no provider (DB persist + Inngest enqueue are Phase 7 TODOs).
  • autoEnrolOnSignal plans but never sends: qualifiesForEnrolment (rejects expired/non-qualifying signals or tier below policy.minTier via TIER_RANK A:3 B:2 C:1 D:0), then upserts an Enrolment; the first message still routes through the gate.
  • costCapStatus is pure: halt = llmUsd>=cap || providerUsd>=cap. readDailySpend sums prisma.providerCost over the UTC day and swallows DB errors as zero so a transient hiccup never causes a false halt.
There is no pipeline.ts The Stream A pipeline (discover → dedupe → enrich → score → rank) exists only as an integration test, pipeline.test.ts, composing waterfall.ts + scoring-bridge.ts + @oie/core. It asserts per-field attribution (sources.placeId === 'places', sources.industry === 'apollo', matchedBy === ['places','apollo']) then runs toScoringSubject + scoreLead + rankByComposite.

The Node-runtime auth.ts spreads authConfig and adds the bcrypt Credentials provider: authorize() lowercases/trims the email, compares AUTH_OPERATOR_EMAIL + bcrypt.compare(password, AUTH_OPERATOR_PASSWORD_HASH), and a dev fallback (dev@oie.local) is gated on NODE_ENV !== 'production' AND ALLOW_DEV_LOGIN === 'true' (fail-closed double opt-in).

08 AI features internals

All three AI surfaces (Close Room, Knowledge, Voice Dojo) are 'use server' actions following one identical pipeline: build a system prompt = feature template + grounding(canon blocks), build a single user turn from real data, then call the one chokepoint ask(). ask() instantiates the @oie/integrations LlmClient and calls .complete(), a hand-rolled REST adapter over the Anthropic Messages API. There is no @anthropic-ai/sdk in the graph.

Figure 8.1 - One AI feature end-to-end (Close Room battlecard): canon grounding -> ask() -> Anthropic -> render

Knowledge and Dojo traces are identical except for the grounded blocks, system template, user turn, tier (Dojo score and Close coach use deep:true = Opus), and maxTokens. The ask() path never passes tools, so toolInput stays null and result.text is the path used.

// apps/web/lib/llm.ts
const DEFAULT_MODEL = MODEL_IDS.personalise;  // claude-sonnet-4-6
const DEEP_MODEL    = MODEL_IDS.hard;         // claude-opus-4-8
export async function ask(opts: { system; user; deep?; maxTokens? }): Promise<string> {
  const model = opts.deep ? DEEP_MODEL : DEFAULT_MODEL;
  const key = (process.env.ANTHROPIC_API_KEY ?? "").trim();   // lazy; throws clean error if empty
  const result = await new LlmClient({ apiKey: key }).complete({
    model, system: opts.system, messages: [{ role: "user", content: opts.user }], maxTokens: opts.maxTokens ?? 2000,
  });  // Sentry.captureException on throw; captureMessage on empty text; key never logged
  return result.text.trim();
}

// apps/web/app/close/roi-math.ts  -  pure, dependency-free, unit-tested
computeRoiMath({ leadsPerMonth, pctUnanswered, avgCommissionAed, closeRatePct }): RoiMath {
  recoveredLeadsPerMonth = leadsPerMonth * pctUnanswered / 100;
  recoveredDealsPerMonth = recoveredLeadsPerMonth * closeRatePct / 100;
  recoveredAedPerMonth   = recoveredDealsPerMonth * avgCommissionAed;
  recoveredAedPerYear    = recoveredAedPerMonth * 12;
}

In computeRoi(input) the math runs first; the user turn is a "COMPUTED GAP (these are the only numbers you may use; show the arithmetic)" block; the ROI_SYSTEM cardinal rule is "frame, never invent. Use ONLY the numbers supplied... If a number needed is missing, write the literal token <CONFIRM>." The returned body prepends a deterministic headline ("Recovered pipeline: AED/month (AED/year)") above the model narrative so the operator sees the payback figure even if the model trims it.

The CallRequest and lead sourcing tie NOVA to the human gate

With no --phone, leads are pulled from prisma.message.findMany({ where: { status: "awaiting_approval" }, include: { enrolment: { include: { contact: { include: { company: true } } } } }, take: 40 }). Each queued Message walks to its contact, runs toE164(c.phone), and is admitted only if dialable and leads.length < Math.min(limit, 5) (limit defaults to 3, hard-capped at 5). The same awaiting_approval human gate used by every other channel means voice calls are only placed against already-approved leads. The POST body literal includes owner_email (default gp@humai.ae), the 4-phase HUSCRIBE_CONTEXT script, goal: "qualify_interest", consent: true, and idempotency_key. place_calls and get_call are public endpoints; the NOVA_API_KEY Bearer only unlocks account features.

// scripts/nova-call.ts  -  toE164 (UAE-specific; returns null for non-dialable)
toE164(raw):  strip non [+digits]
  starts "+"           -> valid only if /^\+\d{8,15}$/ else null
  strip leading "00"
  "971..."           -> +971...
  leading "0"         -> +971 + slice(1)        // UAE national -> E.164
  bare /^(5\d{8})$/   -> +971 + d
  otherwise           -> null                  // 800/toll-free/short codes not dialable

Persistence and the consent-gated enrichment (verify-by-conversation moat)

ingestCallResult looks up the session by novaCallId, defensively coerces status/transcript/summary/outcome/costUsd from multiple payload shapes, computes optOut = optIn ? !affirmative(optIn.value) : false, and updates the row with raw: payload for provenance. Findings are delete-then-recreate: deleteMany then createMany of extractFindings(payload) rows (source: "nova"). Then, only if session.consent:

  • mobile finding: e164 = toE164(value); if valid, prisma.contact.update sets both phone AND whatsapp.
  • tools finding: split on [,/;]| and | & /i, keep 2..40-char tokens, Set-dedupe-merge into Company.techStack, then prisma.signal.create (type tech_adoption, strength confidence ?? 0.6, provider nova, evidence { capturedOnCall, tools }, detectedAt now).

If !session.consent, all enrichment is short-circuited. This is the moat: every consented call enriches the master DB with honest, consented facts that raise the next deterministic score. The anti-corruption layer (extractFindings + affirmative, Section 5) means vendor JSON never leaks into the persistence code; only the seven canonical keys survive, and a missing field yields no finding (missing = unknown, never fabricated).

DEMO_MODE vs live demoMode = !NOVA_KEY is persisted onto every CallSession.create (CallSession.demoMode defaults true in the schema). In demo mode NOVA joins a LiveKit room and no PSTN dial occurs. Flipping to live PSTN is the NOVA owner's action on the NOVA side, gated by owner_email accountability and non-code UAE legal prerequisites. It is not a change in this repo.

12 Invariants and honest scope

The architecture is built around a small set of hard invariants, each enforced structurally rather than by convention. The table separates what is live from what is a deliberate, documented stub or demo.

Hard invariants (enforced in code)

  • The LLM never computes a score. scoreLead is pure with no model input path; @oie/core has zero Anthropic dependency; Score stores numeric fields computed by code with the LLM narrative confined to rationale Json.
  • DRY_RUN defaults true. boolFromEnv(true) resolves missing/blank to true; CI hard-codes it true; it must be explicitly set to a falsy token to live-send.
  • Nothing sends without a passing dry-run AND explicit human approval. evaluateSendGate is the single rail; allowSend === true is the only path to a provider call; DRY_RUN always wins.
  • Vendor shapes never leak into core. Mappers validate and fold every wire shape; the NOVA findings normaliser allowlists seven keys; missing data is unknown, never fabricated.
  • Channels off by default. ChannelAccount.enabled defaults false (LinkedIn/WhatsApp), and the gate blocks disabled channels first.

Live vs demo / stub

  • Live: the scoring engine, the enrichment waterfall + signal fan-in, the Prisma data model, the AI surfaces (Close/Knowledge/Dojo) over the real Anthropic Messages API, Auth.js gating, security headers, the CI verify + secret-scan, and Fly deploy.
  • Stub (documented): the approval-queue server actions are explicit no-send stubs (console.info only; DB persist + Inngest enqueue are Phase 7 TODOs).
  • Demo by default: NOVA runs in DEMO_MODE (no NOVA_API_KEY → LiveKit room, no PSTN dial). CallSession.demoMode defaults true.
  • Off by default: live sending (DRY_RUN true everywhere), LinkedIn/WhatsApp channels (disabled), live PSTN (a NOVA-side owner action with non-code legal prerequisites).
Why these invariants compose The system is safe-by-construction: even with every credential present and the operator clicking approve, a real send still requires DRY_RUN to be explicitly flipped off in validated env, the channel to be operator-enabled, and the action to pass the pure gate. Voice calls inherit the same human gate because they are sourced from awaiting_approval Message rows. Master-DB enrichment from a call is consent-gated. The deterministic scorer cannot be moved by the model. Each guarantee is an independent code-level check, so no single mistake or forgotten instruction can produce an unintended send or a hallucinated number.
